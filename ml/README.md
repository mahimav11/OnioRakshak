# ML Module — OnioRakshak

This module covers all machine learning work for OnioRakshak: turning raw sensor and market data into actionable predictions for farmers — how long stored onions will stay usable, and when to sell for the best return.

## 1. Modules

We're proceeding with three core ML modules:

### 1.1 Shelf-Life Prediction Module
Predicts the remaining usable storage life (in days) of onions based on real-time and historical environmental sensor data (temperature, humidity, gas concentration). This is the primary safety-critical module — it drives the automated actuator alerts (fan, curtain, buzzer) and the "days remaining" indicator on the dashboard.

### 1.2 Storage Risk Classification Module
A lightweight classification layer that buckets current storage conditions into discrete risk categories — **Safe / Warning / Critical** — based on live sensor readings. This sits alongside the shelf-life regressor to give farmers a quick, glanceable status rather than just a numeric estimate, and to trigger immediate actuator responses.

### 1.3 Market Price Prediction Module
Forecasts short-term onion market prices (Rs/quintal) for Maharashtra markets, so farmers can decide whether to sell now or continue storing.

## 2. Datasets

| Module | Data Used | Source |
|---|---|---|
| Shelf-life prediction & risk classification | `data/onion_shelf_life_dataset.csv` — 21,780 rows across 180 storage batches, 3 varieties (Red/Yellow/White), 3 storage modes (Ventilated_ambient/Warm_ambient/DOGR_like), with sensor readings + derived 24h rolling stats + spoilage outcomes | Research-anchored synthetic dataset (used until real ESP32 sensor logs accumulate post-deployment) |

## 3. Data Preprocessing Pipeline

1. **Cleaning** — both datasets are already clean (no missing values), so this step is mainly relevant once real sensor/price data starts flowing in (handling dropout/gaps, deduplication, outlier removal via IQR/z-score).

2. **Standardization** — numeric features are scaled with `StandardScaler` inside each model pipeline.

3. **Categorical encoding** — categorical fields (`variety`, `storage_mode`, `market`) are one-hot encoded.

4. **Feature selection — the important part:** for shelf-life, the raw dataset includes `weight_loss_pct`, `decay_pct`, and `sprouting_pct` as columns, but these are **symptoms of spoilage**, not something our ESP32 + DHT22/MQ135 sensors can measure in the field. They're deliberately excluded from model inputs. For price prediction, features are lag/rolling/calendar-based (see Section 6) rather than instantaneous, since price forecasting is a time-series problem.

5. **Train/test split** — for shelf-life, split by `batch_id` (`GroupShuffleSplit`), not by row, since rows from the same batch share a trajectory. For price prediction, split **chronologically** (train on the past, test on unseen future dates) rather than randomly, since a random split would leak future prices into training.

## 4. Models & Their Significance

### 4.1 Regression — Shelf-Life Prediction
**Random Forest Regressor.** Predicts `remaining_shelf_life_days` as a continuous value. Chosen over linear regression because the relationship between gas/temperature/humidity and spoilage is non-linear, and it gives feature importances for free.

Current result: **MAE ≈ 6.4 days, R² ≈ 0.91**, using only sensor-realistic features. `mq135_gas_index` is by far the strongest predictor, followed by `storage_day`.

### 4.2 Classification — Storage Risk Status
**Random Forest Classifier.** Buckets the same inputs into Safe/Warning/Critical — the discrete signal that drives buzzer/actuator logic and the dashboard's at-a-glance status.

Current result: **94% accuracy**; the "Warning" middle class is the hardest to separate (72% recall), as expected for a narrow band between two easier extremes.

### 4.3 Regression — Market Price Prediction
**Random Forest Regressor** on lag/rolling/calendar features. Predicts next-day modal price; a multi-day-ahead forecast is also implemented by feeding predictions back in iteratively.

Current result (on synthetic data — see Section 6): **MAE ≈ Rs 199/quintal, MAPE ≈ 6.8%, R² ≈ 0.95** for next-day prediction.

All three models use size-constrained hyperparameters (`max_depth`, `min_samples_leaf`) rather than defaults — uncapped trees produced 300+MB model files for negligible accuracy gain, which is impractical for the Appwrite Function deployment these models are meant to run in.

## 6. Important Note on the Price Dataset

`data/maharashtra_onion_price_dataset.csv` is a **research-anchored synthetic dataset**, not scraped real records. It's grounded in documented facts (a published SARIMA seasonality study on Lasalgaon APMC — April price lows, October highs; documented arrivals-price negative correlation; realistic volatility events modeled after real reported crashes/spikes), but it is generated data, not observed data. Treat the price model's results as a working placeholder, not a citable evaluation result.

`scraping/mandi_price_scraper.py` pulls genuine daily Maharashtra onion prices from the government's data.gov.in feed and appends them to a growing history file. This government API only returns "today's" snapshot with no retained history, so this scraper can only build real history forward from whenever it's first run — it can't backfill the past. **Once it has accumulated enough real days (realistically weeks to months), retrain `03_price_model_training.ipynb` on the real file and compare results before reporting anything as final.**

The shelf-life dataset (`onion_shelf_life_dataset.csv`) is similarly synthetic-but-research-anchored, pending real ESP32 sensor deployment.
